# ModelGate 面试话术

> 用途：把项目讲成"我做过流量治理"，而不是"我调过几个 API"。
> 所有数字都来自本仓库的可复现实验（`loadtest/`、`verify/`），被追问时能当场打开代码和日志。

## 1. 一句话定位

> ModelGate 是一个**纯 Java 的 LLM 流量网关**：对上提供 OpenAI 兼容接口，对下屏蔽多家模型供应商，
> 中间完成**路由、限流、缓存、熔断、计量、可观测**六件事。它不是 Agent，也不是 RAG——
> 它是这些应用前面的那一层基础设施。

**叙事关键词（只用这些）**：网关、路由、加权/灰度、限流、配额、语义缓存、熔断、降级、背压、
SSE 透传、压测、P99、JVM、GC 暂停、堆外内存。

**禁止出现**：Agent 编排、工具调用链、RAG 检索、向量库调优（那是另外两个项目的地盘）。

## 2. 岗位覆盖（投递时按岗位换侧重）

| 岗位 | 主打什么 |
|---|---|
| 业务后端 | 三层配额（key/tenant/model）、语义缓存命中率与省钱、JMeter 压测数据、JVM 调优对照 |
| AI 平台 | 多模型接入与 Provider SPI、Token 计量与成本核算、SSE 流式透传与 TTFT、prompt cache 计价 |
| 基础架构 | WebFlux/Reactor Netty、路由与灰度、熔断状态机、可观测性与容量判断 |

## 3. 30 秒版

> 做的是一个 LLM 网关：Spring WebFlux + Reactor Netty，七个模块。
> 上游挂了会自动熔断并切备用模型，请求按 key/租户/模型三层配额限流，
> 相同语义的请求会命中语义缓存直接返回。
> 压到 13.8k QPS 时网关自身开销只有 1ms，P99 从 21ms 降到 14ms 是靠换 ZGC——
> 因为默认 GC 一次停顿 30ms 会直接落到 P99 上。

## 4. 深挖路径（面试官问到哪，就往哪走）

### 4.1 他说"讲讲路由" → 讲三层语义的区分

> 路由里最容易做糊的是把三件事揉成一坨，我是分开的：
> - **retry**：留在同一个 model group 里换 deployment，触发条件是 5xx/429/超时，**4xx 不重试也不计熔断**（那是调用方的错，不是上游的病）
> - **fallback**：跨 group，走配置的备用模型链
> - **cooldown/熔断**：摘掉**单个 deployment**，不是整个 group
>
> 流式的 failover 只在**首个 chunk 之前**成立——已经有字节吐给客户端了再重试就是重复输出。

追问"熔断怎么触发"：
> 两个信号，缺一不可。连续失败 3 次抓硬故障；窗口内失败率 ≥50%（至少 10 个样本）抓"轮流失败"的抖动上游。
> 恢复是 OPEN → 冷却到期 → **HALF_OPEN 只放一个探测请求**，成功才 CLOSED；失败则退回 OPEN 并且冷却翻倍
> （1×→2×→3×，上限 10×），避免对刚崩的上游打出一波惊群。

### 4.2 他说"语义缓存怎么做的" → 讲边界而不是算法

> 阈值默认 0.95，只吃"同一个问题 + 标点空白差异"。实测同一个 prompt 是 1.0000，多一个句号 0.9907，
> 改述就 miss——**0.85 能提高命中率，但会开始答非所问，这个旋钮的取舍要拿 `cache_similarity` 的分布来定**。
>
> 真正要守住的是三个边界：
> 1. **namespace 必须含 key**（`sc:{keyId}:{modelGroup}:{paramsHash}`），否则就是把 A 用户的答案发给 B 用户，这是安全事故不是性能问题；
> 2. **流式不查缓存**——流式答案要全部生成完才知道是不是重复，那时 token 已经花了；
> 3. **缓存不能阻断请求**——embedding 或检索任何异常都降级为正常上游调用并计数。
>
> 另外做了 **in-flight 合并**：冷缓存瞬间 N 个相同请求只打一次上游。压测里 30 秒合并掉 149 万次请求，
> 吞吐 13.8k → 53.8k，P50 从 6ms 降到 1ms。

### 4.3 他说"限流呢" → 讲维度和原子性

> 三层：key → tenant → model，**最具体者先拦**，一个滥用 key 不该吃掉整个租户的额度。
> RPM 用滑动窗口（ZSET + ZREMRANGEBYSCORE），TPM 固定窗口、按**调用完成后的真实 usage** 记账。
>
> 关键设计：**三个维度由同一个 Lua 脚本一次性原子校验**，一次 RTT 而不是三次。
> 实测 Redis 后端相对进程内后端，p50 只多 1ms。
> 单机 vs 集群两套实现共用接口——多副本下限流会漂，这件事必须在简历上写清楚，不能等面试官问。

### 4.4 他说"压测数据是怎么来的" → 讲对照而不是数字

> 上游是自建 Mock（可调延迟、逐帧 pacing、注错），因为**拿真实 API 压测测到的是厂商的延迟，不是网关的**。
> 先跑直连上游做基线，再跑过网关，差值才是网关开销。
>
> 第一次把上游设成 80ms，三组 QPS 都卡在 550 左右——**瓶颈在上游，QPS 横向对比没有意义**。
> 把上游降到 2ms 之后才看出网关自己的上限（13k）。
>
> 指标上我特意加了 `overhead_latency = 端到端 − 上游`：只有它才能回答"慢是网关慢还是上游慢"。

### 4.5 他说"JVM 呢" → 讲一个反直觉的结论

> 我先以为是 ZGC 一定更快，实测打脸：**吞吐 13.1k / 13.9k / 14.8k 三组在噪声范围内**
> （ZGC 同一配置两次跑出 11.6k 和 14.8k，差 27%），**换 GC 换不来吞吐**。
>
> 但 GC 暂停差了两个数量级：ZGC 平均 0.035ms、最长 0.1ms；G1 平均 10ms、最长 27.3ms。
> 默认 JVM 最长暂停 30.7ms，对应的 P99 就是 21ms——**停顿直接翻译成用户感知的长尾**。
>
> 还有两个具体的点：显式固定堆 2g 让 GC 次数从 161 降到 28、总暂停从 522ms 降到 282ms；
> 以及 `-XX:MaxDirectMemorySize`——**流式网关的 ByteBuf 在堆外，只看堆曲线会误判内存压力**。
>
> ZGC 的 `-Xlog:gc` 不打印暂停耗时，得用 `-Xlog:gc*`，这个坑也踩过。

### 4.6 他说"灰度怎么做" → 讲粘性，顺带讲我踩的坑

> 按 API key 哈希分桶，同一个调用方永远在同一臂——否则灰度期间用户会在两个变体之间来回跳，
> 数据既没法归因也会被用户察觉。响应头回 `x-modelgate-arm`，用量表里也记臂，一次 `GROUP BY arm` 就能对比两臂成本。
>
> 这里踩了个坑值得说：**桶不能直接用 `String.hashCode()`**。`key-a`..`key-h` 的哈希是连续的
> （…411、…412、…413），桶号连续，30% 灰度对 `key-a`..`key-s` 实际是 73%——
> 按名字顺序发 key 会让整批调用方一起进同一臂，既不随机也不构成受控的爆炸半径。
> 修法是分桶前过一遍 MurmurHash3 的 32 位 finalizer 做雪崩，同时保持跨副本确定。

### 4.7 他说"计量和成本" → 讲取舍

> 收据走**有界队列 + 后台批量落库**，热路径只做一次 `offer`：
> **一个慢的数据库永远不能让一次推理变慢**。代价是账单最终一致，队列打满会丢记录——
> 所以 `dropped` 这个计数是最该告警的指标（"服务了但没收到钱"）。
>
> 计价不能简单地 tokens × 单价：**prompt cache 命中与写入的倍率不同**（OpenAI 命中 0.5×、写入 2×；
> Anthropic 两边都是 1.25×），所以 canonical 的 `usage.prompt_tokens_details` 要在网关层解析并计价。
> 实测同一段 1000 token 的 prompt，命中 90% 的那一臂成本 0.000097，另一臂 0.000164。

### 4.8 他说"讲讲并发模型" → 讲 Java 栈的差异化

> 流式透传走 WebFlux：上游 SSE 逐帧 `bodyToFlux` → `writeAndFlushWith` 逐帧刷盘，
> **不缓冲整包**，背压沿 Reactor 链路自然传导；上游静默超时用 `timeout` 做 **TTFT/空闲守卫**，
> 归一成可重试的 504 交给路由决策。
>
> 这也是我用 Java 而不是 Python 的核心原因：网关的瓶颈是"大量并发等待上游"，
> 阻塞式客户端 + 虚拟线程和响应式在这里各司其职——而不是一个 asyncio 事件循环扛所有事
> （上游变慢时 CPU 不涨、in-flight 猛涨，按 CPU 扩容就会失效，这是我加 `in_flight` 指标的原因）。

## 6. 加分项：把"踩过的坑"变成设计说明

以下每一条都是真实发生过并修掉的，讲出来比背八股可信得多：

1. **WebFlux 里声明返回 `Object` 时，`ResponseEntity` 不会被解包**，会被当成普通对象序列化——网关的响应是手写 `writeWith` 的。
2. **超时抛的是 `TimeoutException` 不是我的 `UpstreamException`**，不归一就会被当成"不可重试"而绕过熔断。
3. **熔断的 `isAvailable()` 有副作用**（发放半开探测许可），我在做灰度改造时无意中调用了两次，直接把恢复中的部署过滤没了——单测抓到。
4. **分桶不能直接用 `hashCode()`**（见 4.6）。
5. **缓存会掩盖上游故障**：开着语义缓存做熔断演练，相似 prompt 直接命中，请求根本到不了上游。
6. **压测时配额把 QPS 限死了**：key 的上限是 10 万/分钟，30k QPS 跑 3 秒后全是 429，错误率 94%——
   负载 profile 必须把配额关掉，否则测的是 429 路径。
7. **6 位小数会骗过成本对比**：短 prompt 下两臂成本都显示 0.000013，看起来折扣没生效，实际是被四舍五入掩盖了。
8. **流式重试的边界**：已经吐字节的请求不能重试，否则输出重复。
